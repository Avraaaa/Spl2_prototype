# implementation.md — task execution plan / agent contract

**Requirements source:** `docs/requirements/qfd.md` (text of `DataSoft_QFD_General_Requirements5 (3).docx`). Where this plan and the QFD disagree, the QFD wins unless an owner decision recorded here says otherwise.

This plan is intentionally detailed for P0–P2 and skeletal beyond. Only `docs/tasks.json` defines executable task order, allowlisted paths and command gates. The local `scripts/agent-runner.mjs` enforces them. **All tasks begin incomplete.** Progress is updated only after independent gates and reviewer PASS.

## Global automatic execution protocol

- Preflight: validate clean Git working tree, current CLI authentication, Docker availability, no real bank data, and no secrets in worktree. Start worktree from current HEAD.
- Coder reads its one selected task and only relevant docs/files; no unapproved dependency or requirement changes.
- Reviewer runs in a read-only Codex sandbox and judges the code diff plus test evidence. Reviewer verdict is advisory; gates are independently executed by runner.
- Prototype review severity (owner decision 2026-11-14): the reviewer FAILs only blocking defects (cross-bank exposure, auth/permission bypass, privilege escalation, invalid workflow transitions, data loss, missing/broken core feature, crashes on normal use, UI without real endpoints). Non-blocking findings PASS and are appended to `docs/review-backlog.md` for a later hardening task. Gates always block.
- Retry failed review at most twice. If tests fail, runner does not auto-patch tests; stop and record BLOCKED or FAIL.
- Native Windows mode (owner decision 2026-11-14): gates in `docs/tasks.json` run natively via `scripts/dev.mjs` (no Docker). A failing gate's log is returned to the coder for a fix attempt that shares the same `max_review_retries` budget (bounded; existing tests stay protected); when the budget is exhausted the task is BLOCKED. Coder agents read `learning.md` first; the orchestrator updates it after each task.
- Parallel mode (owner request 2026-11-14): up to `policy.max_parallel` (2) runner processes may run tasks whose `depends_on` are complete. Each uses its own worktree and test database (`POSTGRES_TEST_DB`). Integration is serialized by `.agent_runs/merge.lock`: rebase onto current HEAD, auto-resolve only generated files (contract, schema.d.ts, progress.json), regenerate, re-run all gates, then fast-forward. Any other conflict or gate failure leaves the branch for `--integrate` and marks the task BLOCKED.
- Verify no tracked preexisting test is edited/deleted and no CI/AGENTS/security-policy file changed. Match files to allowed paths. Stronger production CI must check against protected branch outside AI control.
- All gates must report actual exit status 0; otherwise STOP without merge. Commits are created by runner only; branch merge must be fast-forward. No auto-push, real email, cloud provisioning or deployment.
- Stop on run limit, model quota, nonzero exit, unsafe request, conflicting specs, dependency download failure, unreadable source, reviewer repeated rejection, tool inability, or unstable tests. Don't loop forever.
- Each task ends with one commit and tracked progress file; restart runner chooses next incomplete task. Run `node scripts/agent-runner.mjs --show` for status.

## Phase 1 — Accounts, roles and tenant isolation

### P1-T1: Role matrix and controlled onboarding
Requirements: N-01..N-04, EX-01, EX-04.
Data model: Organization; User (Django auth), OrganizationMembership (bank + role, unique user/bank/role); DataSoftStaffRole; TemporaryCredential or FirstLoginSetup token; onboarding events. A person may be Officer and Verifier; DataSoft roles are exclusive unless deliberately allowed by policy.
Services: `register_organization`, `create_user`, `deactivate_user`, `assign_role`, `force_password_reset`. Only DataSoft Admin calls admin creation. No public registration endpoint; inactive users have no live access. Temporary credentials are salted/hashed and expire; first sign-in must not expose other API paths until changed. For a real client, request approval to replace emailed plaintext password with one-time setup URL.
Acceptance tests: anonymous 401/403; unprivileged 403 for create; temporary credential expiry, forced-change gate, reset replay; dual Officer+Verifier membership; DataSoft support may work issues but not add users; deactivated users lose access; no raw credentials in logs.
**Interim prototype behaviour (owner decision 2026-11-14, until email is configured):** the temporary password is returned once in the admin API response and shown once in the admin UI; it is never logged or stored in plaintext. Organizations have no official contact email yet. Both are **deferred to P3-T3** and must not be implemented earlier. Do not add any email sending, SMTP settings or contact-email field before P3-T3.

### P1-T1b: Profile maintenance and username change
Requirements: N-01.
Scope: an authenticated user can view and edit a basic profile (full name, email) and change their own username (unique, case-insensitive; password re-entry required); changes append an AccountEvent with old/new values. Organization and roles stay admin-controlled and cannot be changed through the profile API. Deactivation keeps historical actions attributable to the user (no deletes). No email sending (see P3-T3).
Acceptance: user edits own profile only; cannot edit organization/roles/is_active via profile; username uniqueness (case-insensitive) and validation; wrong current password rejects username change; forced-password-change gate still blocks profile edits until the temporary password is changed; two-bank tests show no cross-bank profile access.

### P1-T2: Bank isolation by construction
Requirements: EX-01, EX-02, EX-03.
Add shared `authorized_issues(user)` selector and row-object policy; deny bank switching via forged headers/body/query, direct object ID, attachments, comments, reports, export, notifications and search. Every new domain must use policy. DataSoft scoped aggregate access separately audited.
Acceptance tests at P1: create Bank A and B and test role-matrix membership/organization APIs, guessed organization IDs, direct-object access, bank spoofing via headers/body, and cross-tenant selectors. Issue, attachment, search and export negative tests MUST be added once these domains exist in P2–P5; do not claim they pass before implementation. Internal-only notes never serialized for clients. Add property tests for role matrix later.
Failure: any cross-bank leak halts all subsequent development.

## Phase 2 — Transactional issue lifecycle

### P2-T1: Ticket register, drafts and authorized submission
Requirements: N-05..N-08, N-10.
Models: Product/Module, Request with tenant foreign key and readable sequence (not enumeration for auth), request type, bug evidence, status, version, created_by; IssueEvent append-only with actor and timestamps. Authorized Issue Officer is submitting actor. Draft is invisible to DataSoft intake.
Scope boundary (orchestrator decision 2026-11-14): **file attachments (N-06 attachments, N-08 screenshots/logs) are implemented in P3-T1** together with private, tenant-checked file storage (invariant 8). P2-T1 must not add attachment fields, uploads or UI, and reviewers must not fail P2-T1 for their absence. P2-T1 bug evidence = environment, steps to reproduce, expected and actual results (text).
Acceptance: typed validation, required bug evidence, permanent readable IDs, draft saves/edits; one-click submit records officer+time once, starts Submitted, never a separate bank approval queue. Same-bank related requests only. Add two-bank negative API tests for GET/list/write/draft on the newly implemented issue domain; verify failures cannot reveal other bank IDs.

### P2-T2: Explicit transition service and concurrency
Requirements: N-09, N-12, N-13, N-16..N-19, EX-06, EX-07, EX-11.
Allowed sequence: DRAFT -> SUBMITTED -> ACCEPTED or REJECTED; ACCEPTED -> PENDING -> IN_PROGRESS -> DELIVERED -> AWAITING_VERIFICATION -> VERIFIED -> CLOSED. If verification fails: AWAITING_VERIFICATION -> IN_PROGRESS (record VERIFICATION_FAILED event), then redelivery. Closed issue can reopen within configurable default 30-day period; later submit Recurring with same-bank linkage. Every accept requires a tentative date or explicit unknown flag; deliver requires delivery notes and actual date. Closure DataSoft only.
Implementation: one service per action; atomic `select_for_update` on Ticket; check current version and actor permissions; append event and notification outbox records within same transaction, then commit. Use database timestamps and UTC timezone-aware arithmetic. Don't expose client-visible internal tasks.
Acceptance: table-driven positive/negative role x state transitions including rejection/failed verification/reopen boundary at 29, 30 and 31 days; tentative-date revision history; actual delivery only on delivery; no automatic verification/closure; `409 Conflict` on simultaneous versioned edits; immutable event cannot be changed via API. Test two sessions racing transition in PostgreSQL, not SQLite.

## Phase 7: QFD gap closure for the prototype (owner decision 2026-11-22; email stays deferred to P3-T3)

P7-T3: Comments on workflow actions and attachment quarantine (N-21,EX-05). Acceptance: Every workflow action (submit, accept, reject, assign, deliver, verify pass/fail, close, reopen) accepts an optional comment stored with the history event and shown per visibility rules. Uploaded attachments start QUARANTINED; a pluggable local scanner (default: signature/EICAR + type/size check, no paid service) marks CLEAN or REJECTED; only CLEAN files can be downloaded. UI shows comment field on actions and attachment scan status. Tests including EICAR rejection and cross-tenant download denial. Gate: the task gates in docs/tasks.json.

P7-T4: Bangla suggestion quality and accessible responsive UI (E-02,E-05,EX-10). Acceptance: Synthetic English+Bangla seed fixtures and evaluation tests showing similar-request ranking and label suggestions work for Bangla and mixed text (keyword fallback tokenizes Bangla correctly). Frontend: labelled form controls, keyboard focus states, aria-live for errors, layouts usable at 360px; add unit tests for any pure helpers. Gate: the task gates in docs/tasks.json.

P7-T5: Precomputed versioned embeddings, hybrid retrieval with evidence, tenant kNN labels, vector topic clustering and evaluation harness (E-01,E-02,E-03,E-04,E-05,E-06,E-08,E-09,E-10,E-15). Design follows owner deep-research 2026-11-22: retrieval-first, human-in-the-loop, no LLM, no reranker, no approximate index in v1. Acceptance: Embeddings (multilingual-e5-small, local files only) are computed once from MASKED text with E5 prefixes (passage: for stored requests, query: for drafts) when a request is submitted/edited, via the transactional outbox or an idempotent job; never on the search read path. Store model id, preprocessing version and dimension with each vector; vectors from a different model/version are never compared. A management command backfills missing embeddings. Similar-request retrieval: within the authenticated tenant only, exact (no HNSW/IVF index) pgvector cosine top-40 + lexical top-40 (Postgres simple FTS ts_rank_cd and pg_trgm similarity, enabled by migration) fused with RRF k=60; return at most 5 above a configurable minimum-relevance gate. Lexical-only fallback when ML is offline or vectors missing; submission never depends on ML. Each suggestion includes deterministic match evidence: shared key terms/phrases between the draft and the candidate (no LLM). Label suggestions: tenant-specific weighted kNN over embeddings of that bank's accepted labelled requests, with cap on near-duplicate examples; cold-start labels use the embedded label description as a prototype (lower-confidence, flagged tentative); per tenant x label thresholds with abstention; feedback records accepted, rejected and corrected suggestions. No centroids, examples or caches shared across banks. Topic proposals: per tenant, agglomerative clustering (cosine, average linkage, configurable distance cutoff default 0.3) over stored vectors of recent unlabelled requests (default 90 days), clusters of size >= 3 only, skipped when fewer than 20 eligible requests; titles from cluster c-TF-IDF terms plus representative request snippets shown to admin. Use scikit-learn/numpy/scipy only if already locked for the package; no new dependencies. Evaluation harness: management command over a synthetic English/Bangla/Banglish fixture with graded relevance (2 duplicate, 1 related, 0 unrelated) including hard negatives (same module, different problem); reports HitRate@5, Recall@5, nDCG@5, MRR@5 for lexical vs dense vs hybrid, broken down by language variant, and writes an experiment manifest (model id/revision, prefix scheme, fusion settings, dataset split, metrics). Tests use a deterministic fake embedder and assert hybrid >= lexical on the fixture. Tests: two banks (no cross-tenant results, labels or clusters), ML offline fallback, masking before embedding, no embedding writes during search, version mismatch ignored. Gate: the task gates in docs/tasks.json.

P7-T6: Banglish normalization and embedding model comparison harness (E-02,E-03,E-05,E-09). Acceptance: Deterministic Banglish normalization (versioned): Unicode NFC, whitespace/punctuation cleanup, protected technical tokens (OTP, RTGS, BEFTN, NPSB, error codes like E105, module names) never altered, and a reviewed domain dictionary in a data file mapping common romanized Bangla spelling variants (e.g. ashche/ashe/ashtese, hocche/hoche, partesi/parchi, na) to canonical Bangla forms. Original masked text is always kept; the normalized view is added as a supplemental lexical/embedding input, never replacing user text. No new dependencies (no IndicXlit). Normalization runs after masking and before lexical indexing/embedding; bump preprocessing version so stale vectors are ignored and backfill can re-embed. Model comparison: the evaluation command accepts configurations (embedder path/id, prefix scheme symmetric vs asymmetric, normalization on/off, fusion) and runs a matrix: lexical, dense, hybrid, hybrid+normalization, and any alternative local checkpoints present under ML_MODELS_DIR (e.g. gte-multilingual-base, a Banglish E5 checkpoint); missing checkpoints are skipped with a clear message, never downloaded. Report per language variant (English, Bangla, Banglish, code-switched, typo) and p50/p95 embedding latency, and write the experiment manifest. Expand the synthetic fixture with Banglish variants, typos and hard negatives (same error code, different failure); split by underlying incident before augmentation so no near-clones leak between splits. Tests: normalization preserves protected tokens and is idempotent; normalization improves or does not hurt lexical HitRate@5 on the Banglish fixture with a fake embedder; two-bank isolation unaffected; matrix runner skips missing models. Gate: the task gates in docs/tasks.json.
