P3-T2 — transactional outbox, in-app notifications, email channel (dev console backend), retries, verification reminders.
QFD: N-17, N-20, N-22; invariant 10; ADR docs/adr/0003-outbox.md. Build on the merged issues/workflow domain
(services/api/domains/issues: IssueEvent and the workflow services in workflow.py) and the tenant selectors (see learning.md).

PARALLEL RUN: P3-T1 (comments/attachments/tasks) runs at the same time. Put your lines ONLY here in shared files:
- services/api/config/settings.py INSTALLED_APPS: add your app directly AFTER the line "domains.issues",
- services/api/config/urls.py: add your include(...) directly AFTER the domains.issues.urls line
- apps/web/src/app/App.tsx: nav/bell directly AFTER the "Products" NavLink; routes directly BEFORE the path="*" Route
Do not touch tests/conftest.py. Do not implement comment notifications (comments are P3-T1); expose a notify service they can call later.

Email is deferred by the owner (no SMTP yet): use Django's console email backend by default
(EMAIL_BACKEND env override allowed); never add real SMTP credentials. The outbox must work with email disabled.

Build:
1. domains/notifications app: Notification (recipient user, organization, issue FK nullable, kind, title, body, read_at,
   created_at) for in-app alerts, plus OutboxMessage (channel email|in_app, recipient, payload JSON, idempotency_key unique,
   status pending|sent|failed|dead, attempts, next_attempt_at, locked_until, last_error truncated without secrets).
2. Inside the SAME transaction as each workflow IssueEvent (submit, accept/reject, tentative date change, deliver -> Verifier
   "awaiting verification", verify / verification failed, close, reopen), create in-app notifications for the right users
   (bank Officers/Verifiers of that bank and/or the assigned DataSoft agent / DataSoft staff) plus email outbox rows. Recipients
   are always from the issue's own bank or DataSoft; never another bank. Hook in through a small function called by the
   workflow services. Do not restructure them.
3. Management command `process_outbox`: claims due rows with select_for_update(skip_locked=True) and a lease (locked_until),
   sends via Django mail, marks sent; on error increments attempts with capped exponential backoff, and marks dead after N attempts.
   Idempotent (a sent row is never re-sent). No Celery/Redis.
4. Management command `send_verification_reminders`: for issues in AWAITING_VERIFICATION longer than a configurable number of
   days (setting, default 3), notify the bank's Verifier(s) and the assigned agent once per period (idempotency key per
   issue+day). Never auto-verify or auto-close.
5. API: list my notifications (own only), mark read and mark all read, unread count. Tenant-safe (users only ever see their own).
6. Frontend: a notification bell with unread count in the top bar and a notifications page/dropdown with mark-read, linking to the issue.
Tests: notifications created atomically with events (a rollback leaves none), cross-bank recipients never notified, outbox
retry/backoff/dead-letter, idempotency, a failing email backend leaves the workflow untouched, reminder idempotency, API returns
only own notifications. Never run uv/python/pytest/manage.py/dev.mjs/check-contract in your sandbox. Ruff: PEP 695 generics
without leading underscore.
