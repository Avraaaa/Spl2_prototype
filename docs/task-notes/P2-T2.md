Key QFD details (docs/requirements/qfd.md §1.5 workflow, N-09, N-12, N-13, N-16..N-19, EX-06, EX-07, EX-11):
- Build on the merged issues domain from P2-T1 (services/api/domains/issues: models, services, IssueEvent, api). Read it first; extend, don't duplicate.
- One named service per transition, each in transaction.atomic with select_for_update on the issue, an explicit allowed-from-states set and allowed actor roles, an optimistic version check (client sends `version`; mismatch -> 409 Conflict), and an append-only IssueEvent (actor, kind, from/to status, reason, timestamp) in the same transaction.
- Statuses: DRAFT -> SUBMITTED -> ACCEPTED or REJECTED; ACCEPTED -> PENDING (assignable) -> IN_PROGRESS -> AWAITING_VERIFICATION (set by DELIVER) -> VERIFIED -> CLOSED. Verification failed: AWAITING_VERIFICATION -> IN_PROGRESS (event VERIFICATION_FAILED, reason required) -> redeliver. Reopen: CLOSED -> IN_PROGRESS within a reopen window (default 30 days, admin-configurable setting/model), reason required, by Issue Officer, Issue Verifier or DataSoft; after the window -> 400 telling the client to create a Recurring request.
- Roles (N-04: DataSoft Administrator can do everything a Support Agent can): accept/reject/assign/start/deliver/close = Support Agent or Administrator; verify/fail-verification = Issue Verifier of the same bank; reopen = Officer/Verifier of the same bank or DataSoft. Only DataSoft closes, and only from VERIFIED. No automatic verification or closure.
- Accept requires a tentative delivery date or an explicit "to be provided later" flag; tentative-date revisions are kept as events and visible to the client. Rejection reason is client-visible and required. Deliver requires a delivery note (what changed, version/deployment details) and sets the actual delivery date. Rejected requests cannot be assigned. Assignment: to an active DataSoft user; reassignment recorded.
- Every status change records its timestamp (show the last status update date in the API).
- Tests: table-driven role x state (positive and negative), reopen boundary at 29/30/31 days (freeze time with timezone-aware datetimes; no new dependencies, so patch django.utils.timezone.now), 409 on a stale version, events immutable through the API, two-bank isolation on every transition endpoint (other bank's issue = 404). Race test: use transaction + select_for_update semantics; a real two-connection race is optional if it needs threads (use TransactionTestCase or pytest.mark.django_db(transaction=True)).
- Frontend (apps/web/src/features/issues and features/workflow, routes in apps/web/src/app/App.tsx): on the issue detail page show the timeline (status, actor, date, reason, tentative/actual delivery dates) and role-appropriate action buttons (Accept with date or "later", Reject with reason, Assign, Start, Deliver with note, Verify, Fail verification with reason, Close, Reopen with reason), each calling the real endpoint and sending `version`; show 409 as "This request was changed by someone else — reload".
- Order: backend services + tests first, then API, then UI. Out of scope: comments/attachments/internal tasks (P3-T1), email/in-app notifications (P3-T2; leave a clear hook), reports (P4-T1).
- Ruff: PEP 695 generics without leading underscore. Never run Python in your sandbox.
